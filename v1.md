# v1: record-centric assignment with collective evidence

Written 2026-09-25. It replaces the S1-centric pairwise design in `plan.md` and baseline v0 (`code/business_entity_resolution/src/ber`).
- Background on the task, the metric and the dataset: `understanding.md`.
- Literature notes: `research.md`.

## 1. Why a new design

v0 and `plan.md` are **S1-centric and pairwise**:
1. For each S1, retrieve about 30 S2/S3 records.
2. Score each (S1, record) pair on its own as match or no-match.
3. Afterwards, fix up the result with a greedy "each record to its best S1" step and a global threshold.

v0 has never run on real data. It doesn't scale to ~12M records per split on the g5, can't match across scripts, and doesn't fit the per-entity F0.5 metric.

The data has structure the pairwise design ignores:
1. **Exclusive ownership.** Every S2/S3 record belongs to at most one S1 (0 of 7.64M matched IDs is claimed twice), and about 25% of the pool belongs to none.
2. **Several pool records per business.** One S1 has 3–5 matches on average across S2 and S3. A hard record, such as a Devanagari name or a web-domain name, usually has an easy sibling.
3. **Probably programmatic noise:** leetspeak, domains built from names, glued city suffixes, transliteration, abbreviations. These patterns can be mined from the labelled train pairs instead of guessed.

## 2. S1-centric vs record-centric

Both designs use the same features and model types. The difference is **the question the model answers**.

**S1-centric** asks, per pair: "Is this record a match for this S1, yes or no?"
```
S1 "Sharma Traders Pvt Ltd, 12 MG Road"
   ├─ R1 "Sharma Traders, 12 MG Rd"      → 0.92 ✔
   ├─ R2 "Sharma Textiles, 12 MG Road"   → 0.65 ✔  (above threshold, but R2 belongs to S1 "Sharma Textiles")
   └─ R3 "Verma Stores, 14 MG Road"      → 0.10 ✘
```

**Record-centric** asks, per S2/S3 record: "Which S1 owns this record, or nobody?"
```
R2 "Sharma Textiles, 12 MG Road"
   candidates: "Sharma Textiles" 0.95 | "Sharma Traders" 0.65 | NONE  → owner = "Sharma Textiles"
Distractor D
   candidates: 5 weak S1s                                              → owner = NONE
Record at a French address shared by 101 S1s
   candidates: 101 near-equal S1s                                      → NONE unless the name singles one out
```
Records are then grouped by owner. An S1 that receives nothing gets an empty list, which is exactly right for singletons.

| Problem | S1-centric | Record-centric |
|---|---|---|
| A record wanted by two S1s | Both can accept it; needs fixing afterwards | Impossible: one owner per record |
| Distractors (~25% of the pool) | Several chances to be wrongly accepted, one per S1 that lists it | One decision, with "none" as a trained option |
| Crowds sharing one address (France: up to 101) | Every pair looks strong, so it over-merges; trees can't extrapolate past the train maximum of 14 | Many equal competitors mean low confidence, so it abstains |
| Search cost | 2.2M queries into a ~10M index, about 30 slots each | ~10M queries into a ~2M index, about 10 slots each (each record needs only its one owner) |
| Hard records (Devanagari, domains) | Scored alone | Borrow evidence from easier siblings |

**Downsides of record-centric:**
- The metric is still per S1, so a per-S1 decision step is needed at the end (stage 4).
- There are more parts: a pair model, a record model and an entity model.
- The recall limit is the same: a record whose owner isn't in its top-k is lost.

## 3. Decisions

| Decision | Choice |
|---|---|
| Backbone | **Record-centric assignment**: each pool record picks its owner S1 or *none*, with sibling-consensus features. The benefit of graph clustering comes in through features, not hard clusters |
| Neural depth | **Fine-tuned bi-encoder**: pretrained multilingual-e5 on day 1, then contrastive fine-tuning on train pairs. Cross-encoder and LLM left out for now |
| Compute | **g5 + Modal**: the g5 for GPU work and the final run; Modal big-CPU containers for joins and features; Modal GPUs for embedding shards |
| First hours | **Data forensics first**: mine the noise operators and real statistics before building |

## 4. Architecture

```
0 FORENSICS → CANONICALISATION   mined noise operators + romanisation + address parsing (train pairs only)
1 RETRIEVAL (pool → S1, the small side)
     dense  : multilingual-e5-small → fine-tuned e5; FAISS flat on the S1 index, per country, top-k≈10
     keyed  : DuckDB joins on rare tokens, (postcode, house_no), (rare name token, city); capped blocks
     sibling: pool → pool kNN (same country); only for uncertain records if full kNN is too costly
2 PAIR SCORER     XGBoost on the GPU: canonical-form string sims, embedding cosine, component agree/conflict,
                  multiplicity/genericness, SIBLING CONSENSUS (do my neighbours point to the same S1?)
3 RECORD MODEL    per pool record over {candidates} ∪ {none}: top-1/top-2 scores, gap, #competing S1s,
                  multiplicity, consensus → calibrated P(top-1 is owner) → assign or abstain
4 PER-S1 SET      group assigned records by S1 → entity model P(any match) →
                  expected-F0.5 prefix choice (empty allowed) → vetoes (postcode / house-number conflict)
5 OUTPUT          matching_results.tsv; candidate_pairs.tsv = retrieval lists inverted to S1 (every match included)
```

## 5. Stage details

### Stage 0: forensics and canonicalisation
- **`forensics.py`:** on a sample of matched train pairs (both Latin), align tokens and count the most frequent transformations:
  - abbreviations and legal forms
  - character substitutions (leetspeak)
  - reordering
  - name → domain construction
  - city gluing
  - HTML entities, dba splits
  
  Output: a `substitutions.json` table plus a Markdown report with examples.
- **Script check:** for Devanagari, Telugu and Malayalam pool names matched to Latin S1 names, measure how closely `anyascii` romanisation (ISC licence, offline) matches the S1 name. If there are systematic character errors, learn a small character-mapping fix from the pairs.
- **Address parser:** rules and regexes per observed format, giving `house_no`, `street`, `city`, `state`, `postcode`.
- **France gets hand rules**, since there's no French train data: rue/r., av, bd, pl, rte, imp, ch, and SARL/SCI/SAS/EURL as legal forms. `st` stays unexpanded (Street in the US, Saint in France).
- **Stats** for `understanding.md`:
  - row counts
  - **singleton share**
  - matches per S1
  - script mix
  - empty addresses
  - country agreement between S1 and its matches
  - address-sharing distribution

### Stage 1: retrieval
- **Embeddings.** Adapt `main:src/amlc/features/embed.py` (sharded, resumable text embeddings) for e5, using the `query: ` prefix on both sides for symmetric matching. Fan out on Modal GPUs, adapting `main:src/amlc/modal_app.py`: the `--script` mode, S3 part files and resume-on-rerun.
- **Search.** FAISS flat inner product on the g5, per country, pool → S1, top-k. The S1 index is about 1.1M × 384 fp16 ≈ 0.8 GB, so exact search takes minutes.
- **Fine-tuning** (Friday night). e5-small with multiple-negatives ranking loss, trained on train pairs owned by `other`-group S1s only (dev and hold stay unseen, so their cosine features match test), with hard negatives from stage-1 retrieval. About 1–2 GPU-hours on the g5. Re-embed on Modal and swap it in if the holdout recall and F0.5 go up.
- **Keyed channel** in DuckDB, on a Modal big-CPU container (about 32 cores, 128 GB) or on the g5 if it fits.
- **`candidate_pairs.tsv`** is the inverted union: S1 → every pool record that listed it.
- **Gate:** true-pair recall ≥ 0.98 at k ≤ 10 per pool record on the dev split, reported per channel, per country and per script.

### Stages 2–4: models and decisions
- **Training data:** pool records whose owner is in the dev split, plus distractors (split by hash of their ID).
  - **The S1 index always holds all S1**, so competition looks like test.
  - Grouped 5-fold cross-validation by owner (distractors grouped by their own ID).
- **Pair XGBoost** (`device=cuda`, Apache-2.0) for the pair scores.
- **Record GBM** on record-level features. Its target is "top-1 is the owner" (0 for distractors).
- **Isotonic calibration** on OOF predictions.
- **Entity model and decision:**
  - an entity GBM for "S1 has any match"
  - then the per-S1 expected-F0.5 prefix choice, computed with a small dynamic programme (at most about 10 members per S1 in practice)
  - then vetoes
  - then one conservatism scalar, tuned on the collision set, the only global knob
- **Features are computed in sharded, vectorised form** (rapidfuzz `cpdist`, numpy) on the Modal CPU container when the pair count exceeds what the g5 handles. No per-pair Python loops.

## 6. Evaluation and overfitting control
- **Splits:** train S1 split once, stratified by country and number of matches: **dev 400k** (5-fold OOF) and **locked holdout 200k** (scored only for submission candidates).
- **Report per run** (`evaluate.py` → `report.json` plus a `runs.jsonl` line):
  - macro F0.5 on OOF and holdout, with a **bootstrap 95% CI** (gains below about 0.003 are noise)
  - singleton and matched breakdown, per country, per script, and on the collision set
  - recall per channel
  - calibration error
- **Checks:**
  - nested tuning (folds 1–4 tune, fold 5 checks)
  - **US↔India transfer** (the France proxy)
  - **adversarial train-vs-test validation**
  - **learning curve** at 50k/100k/200k/400k
  - singleton-rate shift compared with the **leaderboard score of an empty submission**, which equals the singleton share of the public test subset
- **Submission rule:** submit only on a holdout gain larger than the CI; never tune on the public leaderboard; log OOF, holdout and leaderboard for every submission.
- **Leakage checks:**
  - no label-derived statistics outside the fold
  - unsupervised fits only on text
  - IDs carry no signal
  - don't exploit row order

### Deviations from the plan (fewer dependencies; everything tested offline)

| Plan | Built | Why |
|---|---|---|
| FAISS for dense search | Exact top-k by matrix multiply (torch on the GPU, numpy on CPU) | Same exact result; the S1 index is small; one fewer dependency |
| DuckDB for keyed joins | pandas inverted index, chunked over the pool, with a document-frequency cap | Enough at this scale; no extra engine |
| `anyascii` for romanisation | Own romaniser for Indic scripts (one offset table covers Devanagari, Bengali, Gurmukhi, Gujarati, Odia, Tamil, Telugu, Kannada, Malayalam) | Handles the inherent vowel, virama and Hindi final-vowel drop, which a character-by-character map gets wrong |
| LightGBM cross-check | XGBoost only | One backend, GPU and CPU |
| Evaluation "dev = records touching dev S1" | **Records split by owner group** (distractors hashed). Only dev records are learned from; dev records get out-of-fold predictions, all others come from the final model; pairs with hold S1s are never trained on | The first version moved dev-owned records into the holdout set and biased both scores |
| Modal fan-out for embeddings | Deferred | Run `v1_02` on the g5 first and read its `time` output; add Modal only if embedding is too slow |
